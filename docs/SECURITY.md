# Security self-assessment

This document is the security self-assessment for the Kassa submission. It covers the design principle, the permission tiers with their code and tests, the thirteen invariants, the threat model, the zero-trust controls, the attack suite, and the known risks. Every control named here points to a code path and, where one exists, a test. Where no code or test exists, the document says so.

Test catalogue and results: [TESTS.md](TESTS.md). Architecture: [ARCHITECTURE.md](ARCHITECTURE.md). Privacy: [PRIVACY.md](PRIVACY.md). Standards mapping: [COMPLIANCE.md](COMPLIANCE.md).

Paths below are relative to the repository root. The API is `apps/api`, shared contracts are `packages/shared`. Test paths written as `test/...` in tables are relative to `apps/api/`.

## Summary

- **Model.** The AI proposes; its one money tool, `propose_order`, only creates a proposal; the other writes are `log_expense` (records spending, I6) and, in business mode, `propose_purchase_order` (a draft PO). It has no payment tool, key or import path (I1). Plain code (`rules/decide.ts`) decides. Money moves only on a passkey signature over the canonical order hash (T2) or inside a mandate or base rules the user signed with a passkey earlier (T1).
- **Independent re-check.** `executeApproval` in `apps/api/src/modules/payments/index.ts` verifies again on its own: approval signature, the user's assertion against its own credential store, the recomputed order hash, payee account and cooling, screening, its own daily cap, and a single-use nonce (I2 to I5, I7, I9).
- **Attack result.** Guarded build paid **0 of 16** attacks; the naive baseline (same intents, no rules or payments checks) paid **16 of 16** (`docs/evidence/attacks.json`, `summary: {total: 16, guardedPaid: 0, naivePaid: 16}`, written by `bun run evidence:attacks` from `apps/api/test/attacks/` and `apps/api/test/naive/`; §6.1). The 16 are A1 to A8 from the spec and A10 to A17, which recreate real incidents (Freysa, Grok + Bankrbot, AIXBT, ElizaOS fake memories, MCP tool poisoning and EchoLeak, the Chevrolet "$1 Tahoe" and Project Vend, salami splitting, "safe account" scams; §6). A9 (swapped supplier bank details) is a business-flow test with no naive row. One A12 case paid before the fix of 2026-10-15 (R30).
- **Above the signed cap the order is refused.** The user must first raise the cap with a passkey (§2, T3).
- **Limits.** Everything is sandbox money. Rules and payments share one process, and all keys come from environment variables (no HSM or KMS). Planner and Reader are scripted in the attack tests.
- **No independent review.** This is a self-assessment by the team. No external security review or penetration test has been done (§7.0).

## 1. Design principle

**AI drafts, code decides, signatures move money.**

- The planner (LLM) holds one money tool, `propose_order`, which creates a proposal. Its other writes record spending (`log_expense`) or draft a purchase order (`propose_purchase_order`, business mode); none creates an approval or payment. It has no payment tool, no key, and no network route to payments or rails (I1).
- Plain code decides. `decide()` in `apps/api/src/modules/rules/decide.ts` evaluates a fixed order of hard rules. The AI cannot lower a risk score or raise a limit.
- Money moves only when the payments module can verify, on its own, either (a) a passkey signature by the user over the exact order hash, or (b) a mandate or base rules the user signed with a passkey earlier. A compromised rules service alone cannot pay (I2).

The design assumes the agent can be fooled, documents and messages can be hostile, webhooks can be forged, and the server can be partly compromised.

### 5.5 Key provider and `USER_KEK` rotation (2026-10-16)

Per-user data keys (DEKs) are wrapped by a `KeyProvider` (`apps/api/src/modules/privacy/keys.ts`):
`kekId()` names the KEK that wraps new keys (stored in `user_keys.kek_id`), `wrap(dek, aad)` and
`unwrap(wrapped, aad, kekId)` are async and never expose the KEK. The AAD is `kassa:dek:v1:<userId>`, so a wrapped key
stays bound to its owner whatever the provider. The default is the env provider: `USER_KEK` (32 bytes, base64), local
AES-256-GCM, exactly the previous behaviour; with `USER_KEK_PREVIOUS` set it also unwraps rows of that KEK, never wraps
with it.

**Rotation.** (1) Deploy with `USER_KEK=<new>` and `USER_KEK_PREVIOUS=<old>`: new keys use the new KEK, old rows still
open. (2) `cd apps/api && bun run kek:rotate --dry-run`, then `bun run kek:rotate`: one transaction, `user_keys` locked
in `EXCLUSIVE` mode (reads go on), every wrapped DEK is unwrapped with the old KEK, wrapped with the new one, unwrapped
again and compared, then written with the new `kek_id`. Rows already on the new KEK are skipped (a re-run is safe),
shredded rows stay shredded, a row under any other KEK aborts with nothing written. Output: the two KEK ids (a
truncated SHA-256, not secret) and row counts, never a key. (3) Remove `USER_KEK_PREVIOUS`. DEKs do not change, so no
ledger entry or sealed field is rewritten and `ledger:verify` is unaffected. Keys are read from the environment only,
never from arguments.

**A KMS provider** (AWS KMS, Google Cloud KMS, Azure Key Vault, an HSM through PKCS#11) would implement the same
interface and be installed at startup with `setKeyProvider(...)`; no SDK is a dependency of this build.
`wrap` calls the KMS encrypt operation (or a local AES-GCM wrap under a data key the KMS generated, envelope
encryption) with the AAD as encryption context; `unwrap` calls decrypt; `kekId()` returns the KMS key version, so
`kek_id` records which version wrapped each row. The KEK then never enters the API process, and KMS audit logs show
every unwrap. Rotation becomes a new key version plus the same re-wrap: a rotation script with a KMS provider as
`from` and `to` (or env as `from` and KMS as `to`, to migrate off the environment variable) calls the same
`rewrapUserKeys(from, to)`. Unwrapped DEKs stay cached in process memory as today, so a KMS outage only blocks users
whose key is not cached yet.

### 6.1 Naive baseline: guarded versus unguarded

### 7.2 Build plan known risks

| Risk (build plan) | Effect | Mitigation |
| --- | --- | --- |
| The user approves a bad purchase | Money moves as the user signed it | Canonical order on the sheet, notification for every payment, 24 h delay for loosening, caps. The user can freeze instantly |
| Phone and biometrics compromised together | Passkey signature can be produced | Mandates limit scope and amount. Payments checks caps and the payee register independently. Freeze and unfreeze (24 h) |
| Dishonest supplier or employee confirms a fake delivery | A payment is approved for goods not delivered | Verified payees, caps, reserve. No delivery confirmation logic exists in the build |
| The AI misreads an amount | Wrong amount proposed | Reader evidence checks (I10), the user sees the amount in the signed order, reconciliation of settlements |
| Everything runs in sandboxes | No real money, no real rail | Stated in the README and in [COMPLIANCE.md](COMPLIANCE.md) |

### 7.4 Limits of the simulated payment rails

- Stripe Issuing runs in test mode. The `fake` issuer uses the same authorization logic with local records. Which one is active depends on `ISSUING_PROVIDER` and whether Stripe keys are present.
- The mock bank is in-memory and resets on restart. Its records are not a bank's books.
- The QR wallet is a page labelled "QR Wallet (simulated)". No payment network is involved.
- No payment reaches a real account.
