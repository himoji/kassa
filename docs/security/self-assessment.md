## Summary

- **Model.** The AI proposes, code decides. The one money tool, `propose_order`, submits a draft that `rules/decide.ts` decides. AUTO (inside a passkey-signed mandate or the signed small-auto limit) executes in the same call through the executor registered at startup; anything else only creates a proposal. Other writes: `log_expense` (I6) and, in business mode, `propose_purchase_order` (a draft PO). The agent has no payment tool, no key and no import path to payments or rails (I1). Money moves only on a passkey signature over the canonical order hash (T2) or inside a mandate or base rules the user signed earlier with a passkey (T1).
- **Independent re-check.** `executeApproval` in `apps/api/src/modules/payments/index.ts` re-verifies the approval signature, the user's assertion against its own credential store, the recomputed order hash, payee account and cooling, screening, its own daily cap and a single-use nonce (I2 to I5, I7, I9).
- **Attack result.** Worst case per attack on the guarded build (real modules, scripted planner and Reader that obey the attacker): **7 of 16 refused** by code, **8 of 16 asked** (a passkey prompt on the exact canonical order; nothing moves unless the user approves), **1 of 16 paid**: A5, a QR code swapped inside the external wallet after Kassa's check, which Kassa detects (`HANDOFF_PAID_MISMATCH`, never marked SENT) but cannot stop. With a fooled user who approves every prompt, the attacker is paid in **5 of 16**, against **11 of 16** for a chatbot with a payment tool and one confirm tap per payment (`docs/evidence/tap-confirm-baseline.json`). The naive baseline (raw intent, no checks, no confirmation) pays **16 of 16** by construction and is only the upper bound (`docs/evidence/attacks.json`, `summary: {total: 16, guardedRefused: 7, guardedAsked: 8, guardedPaid: 1, guardedPaysAttackerIfUserApproves: 5, tapConfirmPaidToAttacker: 11, naivePaid: 16}`, written by `bun run evidence:attacks` from `apps/api/test/attacks/` and `apps/api/test/naive/`; §6.1). The 16 are A1 to A8 from the spec and A10 to A17, which recreate real incidents (Freysa, Grok + Bankrbot, AIXBT, ElizaOS fake memories, MCP tool poisoning and EchoLeak, the Chevrolet "$1 Tahoe" and talked-into discounts, salami splitting, "safe account" scams; §6). A9 (swapped supplier bank details) is a business-flow test with no naive row. One A12 case paid before the fix of 2026-10-15 (R30).
- **Above the signed cap the order is refused.** The user must first raise the cap with a passkey (§2, T3).
- **Limits.** Sandbox money only. Rules and payments share one process; all keys are environment variables (no HSM or KMS). Planner and Reader are scripted in the attack tests.
- **No independent review.** No external security review or penetration test has been done (§7.0).

## 1. Design principle

**AI drafts, code decides, signatures move money.**

- The planner's one money tool, `propose_order`, submits a draft; code decides it. REFUSE and ASK create only a proposal; AUTO executes in the same call. The model never chooses whether money moves. `log_expense` and `propose_purchase_order` create no approval or payment. No payment tool, no key, no network route to payments or rails (I1).
- `decide()` in `apps/api/src/modules/rules/decide.ts` runs a fixed order of hard rules. The AI cannot lower a risk score or raise a limit.
- Payments must verify on its own either (a) the user's passkey signature over the exact order hash, or (b) a mandate or base rules the user signed earlier with a passkey. A compromised rules service alone cannot pay (I2).

Assumptions: the agent can be fooled, documents and messages can be hostile, webhooks can be forged, the server can be partly compromised.

### 5.5 Key provider and `USER_KEK` rotation (2026-10-16)

Per-user data keys (DEKs) are wrapped by a `KeyProvider` (`apps/api/src/modules/privacy/keys.ts`): `kekId()` names the KEK for new keys (stored in `user_keys.kek_id`); async `wrap(dek, aad)` and `unwrap(wrapped, aad, kekId)` never expose the KEK. AAD `kassa:dek:v1:<userId>` binds a wrapped key to its owner. Default: the env provider, `USER_KEK` (32 bytes, base64), local AES-256-GCM; with `USER_KEK_PREVIOUS` set it also unwraps that KEK's rows, never wraps with it.

**Rotation.** (1) Deploy with `USER_KEK=<new>` and `USER_KEK_PREVIOUS=<old>`. (2) `cd apps/api && bun run kek:rotate --dry-run`, then `bun run kek:rotate`: one transaction, `user_keys` locked `EXCLUSIVE` (reads continue); each DEK is unwrapped with the old KEK, wrapped with the new, unwrapped again and compared, then written with the new `kek_id`. Rows already on the new KEK are skipped (re-run is safe), shredded rows stay shredded, a row under any other KEK aborts with nothing written. Output: the two KEK ids (truncated SHA-256) and row counts, never a key. (3) Remove `USER_KEK_PREVIOUS`. DEKs do not change, so no ledger entry or sealed field is rewritten and `ledger:verify` is unaffected. Keys come from the environment only, never arguments.

**A KMS provider** (AWS KMS, Google Cloud KMS, Azure Key Vault, an HSM via PKCS#11) would implement the same interface, installed at startup with `setKeyProvider(...)`; no SDK is a dependency of this build. `wrap` calls KMS encrypt (or envelope encryption) with the AAD as encryption context, `unwrap` calls decrypt, `kekId()` returns the key version. The KEK never enters the API process and KMS audit logs show every unwrap. Rotation is a new key version plus the same `rewrapUserKeys(from, to)` (KMS to KMS, or env to KMS to migrate off the variable). Unwrapped DEKs stay cached in memory, so a KMS outage blocks only users whose key is not cached.

### 6.1 Naive baseline: guarded versus unguarded

The naive harness (`apps/api/test/naive/`) executes each attack's raw intent through a stub rail with no rules, payments verification, Reader or webhook checks; it pays by construction and shows what each attack would do unchecked, not a rival product. The guarded column runs the real modules with a scripted planner and Reader that fully obey the attacker (no real AI calls). The fairer comparison is the tap-to-confirm baseline (`apps/api/test/naive/tap-confirm-baseline.test.ts`, `docs/evidence/tap-confirm-baseline.json`): a chatbot with a payment tool where each payment needs one confirm tap and nothing else (no payee register, cooling, verified payees, caps, mandate scope or signature binding the tap to the order). `bun run evidence:attacks` writes `docs/evidence/attacks.json` and `docs/evidence/naive-baseline.json`. Worst-case classes: REFUSED (nothing to approve), ASKED (passkey prompt on the exact canonical order), PAID (attacker paid without the user approving a payment to them).

Result (2026-10-19): **guarded 7 refused, 8 asked, 1 paid** (A5); with a fooled user who approves every prompt the attacker is paid in **5 of 16** (A2, A5, A10, A16, A17; in A2, A10 and A16 the user added the attacker's account and approved it after the 24 h cooling, in A17 at most the per-payment cap). **Tap-to-confirm: 16 of 16 paid** with a fooled user, **11 of 16 to the attacker**; a careful user who declines every card still loses 1 (A3, a forged confirmation row). **Naive: 16 of 16** by construction. The paying A5 case is a swap inside the external QR wallet after Kassa's check and the user's approval: recorded (`HANDOFF_PAID_MISMATCH`, never SENT) but not stoppable. Before the A12 fix of 2026-10-15, one guarded A12 case paid (R30).

### 7.4 Limits of the simulated payment rails

- Stripe Issuing runs in test mode; the `fake` issuer uses the same authorization logic with local records. Which is active depends on `ISSUING_PROVIDER` and whether Stripe keys are present.
- On deployed builds the mock bank keeps state in the deployment's Postgres (migration 0024, `apps/mock-world/src/store`; in memory for local runs and tests), surviving restarts and shared by every instance until `POST /api/demo/reset`. Its records are not a bank's books.
- One-time card charges move simulated money: when Kassa's issuer approves an authorization (merchant, amount cap, expiry, single use), the mock bank debits the wallet in the same step, from the card-currency balance or, if short, the cheapest other balance at the mock bank's quote; if nothing covers it, the authorization is declined `INSUFFICIENT_FUNDS`. The debit is idempotent per authorization id and a single-use card is debited at most once. With the Wise sandbox no card debit happens, and a debit whose confirmation is lost twice is not reversed automatically.
- The QR wallet is a page labelled "QR Wallet (simulated)"; no payment network is involved.
- No payment reaches a real account.
