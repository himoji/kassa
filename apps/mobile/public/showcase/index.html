The same 16 attacks. Kassa refused 7, asked on 8, paid 1.

Sixteen attacks, including recreations of real AI-agent money incidents, each run with the same attacker intent through Kassa's rules, payment checks and document Reader, and through a chatbot whose payment tool needs only a confirm tap. The planner and Reader are scripted to obey the attacker, so this measures the guards, not the model's luck. Every case is marked refused (code stopped it), asked (a passkey prompt on the exact order: nothing moves unless the user approves, and a fooled user might) or paid.

Every proposal, approval and payment is appended to a hash chain with signed checkpoints. This is an illustrative copy: real event types, simplified fields, hashes computed live in your browser with SHA-256. Edit an amount and run the check.

Real runs: the business story has 55 entries and 2 signed checkpoints (docs/evidence/ledger-verify.json); the student tuition run has 12 entries, verified (docs/evidence/sim/tuition-e2e.json). A signed head anchor also catches a truncated tail.

Sources. Attack results and both baselines (tap-to-confirm chatbot, no-checks agent) come from apps/api/test/attacks and test/naive; incident write-ups and citations are in docs/security/self-assessment.md §6. Tiers T0–T3 with code paths and tests: §2.

Everything runs on sandbox and simulated rails. No real money moves, and all companies are fictitious. The attack runs use scripted models that obey the attacker. A live-model run on the judge build (7 turns, all answered by the live model, 3 prompt-injection attacks, none of which paid an account the attack introduced) is committed in the repository as docs/evidence/live-agent.md (raw record: live-agent.json).
